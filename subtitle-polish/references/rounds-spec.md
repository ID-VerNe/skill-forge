# 轮次规范：自动审校的 10(+1) 轮疗程

本文件规定**自动审校模式**的轮次结构。`auto-flow.md` 描述的是**一轮（round）内部**的
阶段 0→11，本文件描述**多轮之间**怎么排、怎么记账、怎么回滚、什么时候停。

两件事分开之后，「跑几轮」和「每个门停不停」变成两个独立开关：

| | 逐步（默认） | 无监管（`--auto`） |
|---|---|---|
| 手动模式 | M0→M6，dry-run 通过即 accept | 不适用（本来就无人干预） |
| 对轴模式 | A0→A5，改动前看 dry-run 预览（见 `align-flow.md`） | 不适用 |
| **自动审校** | **R1→R11 逐轮跑，门 1 / 门 2 每轮停** | **R1→R11 一次跑完，最后出总账** |

`--auto` 只改变「门的处置」，不改变轮次、不改变判据、不改变出片粒度。

## 1. 轮次表

| 轮次 | 名称 | 审计范围 | 默认 | 开关 |
|---|---|---|---|---|
| R1 | 整体第 1 遍（粗） | 全 7 类，粗筛 | ✅ | — |
| R2 | 整体第 2 遍 | 全 7 类，只看上轮残留 + 新发现 | ✅ | — |
| R3 | 整体第 3 遍 | 全 7 类，收敛确认 | ✅ | — |
| R4 | 第 1 类专轮 | 只看结构性生产缺陷 | ✅ | — |
| R5 | 第 2 类专轮 | 只看漏译 | ✅ | — |
| R6 | 第 3 类专轮 | 只看语义反转 | ✅ | — |
| R7 | 第 4 类专轮 | 只看语境错译 | ✅ | — |
| R8 | 第 5 类专轮 | 只看专名错误/不一致 | ✅ | — |
| R9 | 第 7 类专轮 | 只看低严重度（信达雅三轴） | ❌ | `--with-low` |
| R10 | 整体收口 | 全 7 类，专看前 9 轮残留 + 交叉污染 | ✅ | — |
| R11 | 第 8 类专轮 | 中立与合规（性别/宗教/政治/法律；清单是起点不是判据，C 子域只标注） | ❌ | `--with-inclusive` |

**第 6 类（原文拼写错误）默认任何一轮都不跑**，显式 `--with-spelling` 才并入 R1–R3 与 R10。
理由：改它动英文轨，而 `pipeline-spec.md` 规定 SRT 是权威源、skill 不写 SRT。
默认跑会让 10 轮里有一轮在做一件用户没授权的事。

默认疗程 = R1–R8 + R10，**9 轮**。开 `--with-low` 与 `--with-inclusive` 才是 11 轮。

### 1.1 顺序依据（已定）

**R1–R3 打头**：先把大面积、跨行、跨集的问题收掉。后 8 轮的分类专轮才有干净盘面。

**类别专轮排在整体三轮之后**：第 5 类专轮只看专名，若前置整体轮没把「结构性错位」
（第 1 类）收掉，专名专轮会在错位的盘面上判「前后不一致」，报出的不一致里混着错位的假象。

**第 7 类固定 R9（不是"低优先级排最后"，是判据依赖）**：

第 7 类判的是「这句话读起来顺不顺」。而 R4–R8 会**改写句子内容**——专名定名一换
（`MX-5` → `马自达 MX-5`），原句节奏就变了；语境错译一修，后半句断句点也跟着移。
若第 7 类排在 R4–R8 之前，它打磨出的「顺口版本」会被后面几轮整体作废，
等于白跑一轮，还会在台账里制造一批假「连续改动」。排到 R9 = 所有内容定稿后，
再对**最终文本**做最后一次润色，R10 随后检查「润色有没有把语义带偏」，顺序形成闭环。

**第 8 类独立 R11，不并入 R10**：
1. 判据与前 7 类完全不同，混在收口轮里会让 agent 在两种模式间切换，两头都判松；
2. 本轮产出的是**建议**（L3 只标、L4 默认不改、C 子域全 flag），跟收口轮的「定案」性质不同；
3. 独立成轮才能单独统计命中率与误改率，给清单迭代提供分母。

**R11 的流程与 1–7 类完全相同**：并行 subagent 通读切片、自己下判断，不是「脚本判定、agent 只归类」。
区别只在多两步——开工前用 `scan_seed.py` 出锚点喂进 `{seeds}`，收工后主 agent 再拿锚点对照找漏。
锚点只提供位置，**L1/L2/L3 的结论必须由读过上下文的 agent 自己给**；`scan_inclusive.py` 的
词表命中同样只是线索，它返回 0 条时报告里只能写「词表无命中」，不许写「本类无问题」。

R11 内部按子域 A/B/C/D 分四段输出，**C 段（政治与主权）只出 flag 表、不出改动表**，
不进 `fixes.json`。C 子域要落盘需另外显式 `--with-politics`，且仍须在门 2 逐条确认。

## 2. 出片粒度：全量，不取样

**类别专轮一律全量出片**：R4–R9、R11 都是「只审这一类，但看全片」。
**「全量」还有一个含义：全量通读，不是全量给脚本扫。** 抽样会漏，只让脚本扫也会漏——
正则的召回上限就是它自己写下的那几个词。两者都要避免：片要整片读，判断要人（模型）来做。

明确禁止的省 token 做法：只切含专名的块、只抽含数字的块、按关键词命中率采样。
理由：

- 取样会把判据的两种错误（漏报 / 误报）同时放大，而专名误判的代价高于重复审计的代价；
- 采样规则本身需要验证，等于用一个新的不确定判据替换一个已知判据。

token 不是本项目的稀缺资源，**精确**才是目标。这条是硬约束，不留给执行时临时判断。

`round_scope` 只改**审计 prompt 里的类别清单**（`prompts/audit.tmpl` 的 `{round_scope}`），
不裁剪切片文件。切片仍然一次切好、各轮共用。

**切分单位是切片文件，不是类别。** 一个 subagent 负责一个 `[start_block, end_block]`，
在自己那一整片内把本轮所有类别一起过。理由是上下文只有一份——同一句话要判「专名对不对」
与「语气得不得体」，读第二遍纯属浪费，且两次判断可能互相矛盾。片数按
`max(1, round(块数/700))` 取，≤200 块的主 agent 直接审，>200 块必须起 subagent，
**不许因「我已经读完整切片了」自行放宽**。详见 `references/subagent-delegation.md`。

## 3. 每轮的六道闸

全部复用现有脚本，**不新增文本判据**。

| 闸 | 脚本 | 失败含义 | 逐步模式 | 无监管模式 |
|---|---|---|---|---|
| `gate_out` | `apply_fixes --dry-run` | fixes 定位失败 / 撞车 | 停下给人看 | 本轮 skip，不执行 |
| `gate_in` | `apply_fixes --accept --batch-id <唯一>` | 写入失败 | 报错停 | 本轮 skip |
| `gate_ver` | `verify_fixes --batch-id` | 盘面 ≠ log | 停下给人看 | **回滚本轮快照**，本轮 skip |
| `gate_cross` | `cross_check --batch-id` | 撞车预警 | 人看每条预警 | 不阻断，进总账待裁 |
| `gate_reg` | `regression_check --ledger --conflicts` | 同一行连续改动 | 人看 | 标记；下一轮 prompt 强制贴台账 |
| `gate_axis` | `timeline_gate`（有片源时） | FAIL / AMBIGUOUS | 停 | **整体定格** |

`UNVERIFIED` 不进闸：没有片源跑不了闸门属常态，只在总账顶栏写「本次未验时间轴」
（`lib/verdict.py` 的语义是「没验」，不是「通过」）。

## 4. 定格规则（无监管模式）

| 触发 | 动作 |
|---|---|
| `gate_ver` 失败 | 回滚本轮快照 → 后续照跑，总账标该轮 `rollback` |
| `gate_axis` FAIL / AMBIGUOUS | **整体定格**：后续轮次全 skip，总账顶栏置顶 |
| 单轮改动数 = 0 | 不 skip，记 `no_finding`，继续（类别专轮无发现是正常结果） |
| 同一行被连续 3 轮改动 | **冻结该行**：后续轮次不得再改，总账进「争执行」交人裁 |
| 某轮改动率 > 30%（改动行 / 总块数） | 不执行，回滚 + skip，总账写「该轮建议发散，需人工」 |

最后一条是在防「发散轮」：一轮把三成以上的行都判成问题，大概率不是字幕错得多，
是这一轮的 prompt 或盘面出了问题，继续叠下去只会污染后面所有轮次。

## 5. 快照与回滚

### 5.1 目录

```
.subtitle-polish/runs/<stamp>/
├── manifest.json         # 轮次状态机（见 5.2）
├── round-plan.json       # 本次实际排出的轮次表（开关决定）
├── r00.ass               # 第 0 轮 = 起点，逐字节快照
├── r01.ass ...           # 每轮**执行结束后**的快照（skip 的轮次不产生新快照）
├── logs/
│   └── rNN.jsonl         # 该轮 log.jsonl 的整本快照（回滚时逐字节还原）
├── rounds/
│   └── rNN/{fixes.json, dry-run.md, verify.md, cross-check.md, fresh.jsonl}
├── working/              # 逐轮执行时用的 log 副本（见 5.3）
└── final-report.md
```

### 5.2 manifest.json

```jsonc
{
  "run": "20261101_231500",
  "ass": "E:/sub/S06E04.ass",
  "srt": "E:/sub/S06E04.srt",
  "media": "E:/media/S06E04.mkv",
  "opts": {"with_low": false, "with_inclusive": false, "with_spelling": false,
           "gated": false},
  "created": "2026-11-01T23:15:00",
  "frozen": null,             // 定格时写 {"at": "r08", "reason": "gate_axis FAIL"}
  "frozen_rows": [412, 987],  // 连续 3 轮改动、被冻结的 srt_id
  "rounds": [
    {"id": "r01", "name": "整体第1遍", "scope": [1,2,3,4,5],
     "batch_id": "20261101_231512", "n_fixes": 27,
     "verdict": "keep",       // keep | rollback | skip | no_finding
     "snapshot": "r01.ass", "note": ""}
  ]
}
```

`verdict` 五态语义：

- `keep` —— 执行了、验证过了，快照是本轮的；
- `rollback` —— 执行了但 `gate_ver` 失败，已回滚到**上一轮快照**；
- `skip` —— 没执行（`gate_out` 失败 / 改动率超限 / 已定格）；
- `no_finding` —— 执行了，0 条改动（正常，尤其类别专轮）；
- `pending` —— 还在跑。

### 5.3 回滚按快照，不按 log 反向应用

```bash
# 回到第 3 轮末（ASS 与 log 都还原）
python <skill>/scripts/round_orchestrator.py --run <stamp> --rollback-to r03
```

**为什么不用 `apply_fixes --rollback batch=` 逐轮反向应用**：多轮叠加后会撞上三个既有限制
（`pipeline-spec.md` 回滚节已列）——

1. `retime` / `retime_curve` 的浮点累积不可逆（反向应用会留下 0.3ms 级残差）；
2. `delete` 无法自动重建（原文只在 log 里，重建要猜样式与标签）；
3. `global_replace` 与 `apply_fixes` 的交叉（同一行被两种手段先后改过）。

快照整文件还原是确定性的，且与「回到第 N 轮末」这个语义一一对应。
**log 快照 `logs/rNN.jsonl` 必须跟着还原**：否则后续回滚、`verify_fixes --all`、
`regression_check` 看到的台账会包含已被撤销的改动，台账就不干净了。

### 5.4 逐轮执行时的工作目录

为避免与用户手工操作的 `.subtitle-polish/log.jsonl` 互相污染，`--auto` 一轮执行时：

1. `logs/rNN.jsonl` → 作为本轮起始台账写入 `working/log.jsonl`；
2. 本轮 `apply_fixes --accept` 追加到 `working/log.jsonl`；
3. 本轮结束：`working/log.jsonl` → `logs/rNN.jsonl`（覆盖）。

逐步模式不隔离（人就在旁边看着，命令是自己敲的）。

## 6. 最终报告 `final-report.md`

无监管模式跑完后出这一份。它是**可以逐条否决的账**，不是「已改好的字幕」。

```
─ 顶栏     轮次 9/11 跑成 / skip 2 / 时间轴 UNVERIFIED / 净改动 312 行
─ 逐轮摘要  轮次 | 名称 | 类别 | 发现 | 修 | verdict | 沉住度 | batch_id
─ 争执行   被 ≥2 轮改过的行：逐轮文本 + 每轮理由 + 一条命令回滚到任一版
─ 改动总账  srt_id | ass_time | 英文 | 原译 | 终译 | 类别 | 轮次 | 回滚命令
─ 白名单    第 8 类命中但按 L4 白名单未动的行（防"漏改"误读）
─ 未覆盖    第 6 类 / 第 7 类 / 第 8 类 / 时间轴（按实际开关如实写）
```

**「沉住度」** = 该轮改的行里，后来又被改过的比例（`regression_check` 的 `churn`）。
它给轮次结构提供了唯一可观测的精度指标：某一类专轮沉住度常年 < 50%，
说明那一类的**判据本身**有问题，该改规则，而不是继续跑轮次。

**「未覆盖」一节是必须的**：默认不跑第 6/7/8 类是设计决定，不是遗漏。
报告必须把它写出来，否则下一轮人看到「10 轮跑完」会以为这些类也审过了。

## 7. 挑完之后怎么退

| 想退的量 | 命令 |
|---|---|
| 整轮（回到第 N 轮末） | `round_orchestrator.py --run <stamp> --rollback-to rNN` |
| 单条 | `apply_fixes.py --rollback id=<srt_id> --file <ass>` |
| 整个 run（回到起点） | `round_orchestrator.py --run <stamp> --rollback-to r00` |

**每次 `--rollback-to` 都会把 `logs/rNN.jsonl` 写回 `.subtitle-polish/log.jsonl` 与
`working/log.jsonl`**，所以退完之后台账与快照是一致的，可以直接接着跑下一轮。

单条回滚**不受** `run` 目录管理（它走 log），所以单条退完之后台账与快照会不一致——
这是已知的、可接受的：快照只用于整轮退，单条退的账由 `verify_fixes --batch-id` 复核。

## 8. 与逐步（默认）模式的关系

逐步模式**不用** `runs/<stamp>`，行为与 v1.10.0 完全一致：一轮 0→11、门 1 / 门 2 各停一次。
想逐轮跑，就是把这个流程重复 N 次，每次换 `round_scope`。

两种模式共用 `batch_id` 纪律：**每个 batch_id 唯一**，一轮一个。
不要在逐步模式里复用上一轮的 batch_id —— `verify_fixes --batch-id` 会把两轮的记录合并验。
