# 踩坑清单：写脚本 / 喂 subagent 前先读这一页

本页只列**会静默出错**的事实——写错了不报错、报告上看起来正常、事后极难归因的那几种。
每条都给「现象 → 为什么 → 怎么绕」。

不属于本页的：编码风格、目录约定、参数命名规范——那些写在 `SKILL.md` 与各 `references/*.md` 里。

## 1. ASS 时间戳只有厘秒，两位小数就是全部精度

### 现象

写的 `0:00:10.30` 读回来是 `10.30`，写的 `10.2996` 一存盘变成 `10.30`；再读再存一轮，
某些值会**再往下漂一位**，而文件照样能被播放器打开，报告上也看不出任何异常。

### 为什么

- ASS 的时间格式是 `H:MM:SS.CC`，**CC 是厘秒（1/100 秒）**，不是毫秒。
  SRT 是 `HH:MM:SS,CCC`（毫秒）。两者不是同一个刻度，来回转必然丢精度。
- `pysubs2` 内部统一存**毫秒整数**（`SSAEvent.start` 是 int）。任何带小数的秒值
  在 `make_time` / 存盘时都会被压成整数毫秒，再截到厘秒。
- Python 的 `round()` 是**银行家舍入**，碰上 `.xx5` 不是四舍五入。

实测（本机 Python 版本下）：

```python
round(1.005, 2)   # -> 1.0     不是 1.01
round(0.005, 2)   # -> 0.0     不是 0.01
```

因为 `1.005` 的浮点实际是 `1.00499999...`，压根到不了 `.5`。

### 怎么绕

- **改时间的唯一写法是毫秒整数**，与 `pysubs2` 内部一致：

  ```python
  e.start = int(round(new_start * 1000))
  e.end   = int(round(new_end   * 1000))
  ```

  `apply_fixes.py` 就是这么写的（约 207 行处）。不要在毫秒里掺小数。
- **要输出 ASS 时间串**，走 `lib/time_fmt.seconds_to_ass()`，它自己处理 `cs == 100` 进位。
  不要自己拼 `f"{h}:{m}:{s:.2f}"`——那样得不到 `MM:SS` 的零填充，也漏掉进位。
- **比对两个轨的时间**永远在**秒**或**毫秒**上比，不要在格式化后的字符串上比。
  `0:00:10.30` 和 `0:00:10.3` 用字符串比是不相等的。
- **不要用「偏差 0.00s」证明配对正确**。厘秒精度下，0.00 的含义只是「差不到 5ms」。
  E03 实测：全轨 `|zh.start − en.start|` 恒为 `0.00`，而中文轨从第 149 行起**整体错位 39.84 秒**
  ——两轨各自内部时间是对的，只是内容配错了行。这种错位在偏差统计里完全不可见。

## 2. `track` 是中文串，而且样式名会骗人

### 现象

`e.style == "中文"` 判轨道，在别人给的片子上一律失效；更坏的情况是
**它不失效、但它判错了**——整份文件的译文列显示成英文，或者某几行被悄悄跳过。

### 为什么

`style` 是字幕制作者随手起的名字，没有任何规范。本项目固定用三个值：

| 常量 | 值 | 来源 |
|---|---|---|
| `TRACK_EN` | `"英文"` | `lib/ass_srt_pair.py` |
| `TRACK_ZH` | `"中文"` | 同上 |
| `TRACK_NOTE` | `"注释"` | 同上 |

而 `style_to_track()` 是**容错的**：认 `eng`/`english`/`en`/`zh`/`cn`/`chinese` 等别名，
然后退化到**字符串包含**：`` `"英"` in style `` 判英文、`` `"中"` in style `` 判中文。

容错本身是必要的（不然遇到 `Eng` 就全挂），但它制造了两类坑：

```python
style_to_track("中nning? It's runni文")   # -> "中文"   ← 样式名被污染，仍然判成了中文
style_to_track("CHS")                     # -> "CHS"    ← 认不出，原样返回
style_to_track("简体")                     # -> "简体"   ← 认不出，原样返回
style_to_track("Default")                 # -> "Default"← 认不出
```

第一种（E03 `#1314` 实测）最危险：样式名里混进了一句英文台词，`"中"` 还在，
于是这行被当成中文轨收下，内容却是英文。报告上看不出任何异常。

### 怎么绕

- **判轨道永远走 `style_to_track()`**，不要各处自己写 `if "中" in style`。
- **要判「样式名是否干净」用严格口径**，不要用容错口径：

  ```python
  ok = mapped in VALID_TRACKS and len(raw) <= 4 and not re.search(r"[A-Za-z0-9]", raw)
  ```

  `structure_check.check_track_enum()` 用的是这一条。它在 E03 上抓到了 `#1314`，
  而容错口径放行了。
- **认不出的样式名不要猜轨**。`show_ids.py` / `scan_inclusive.py` 遇到认不出的一律
  打 stderr 警告；`scan_inclusive.py` 在**整份文件一个都认不出**时才退化为
  「含汉字即中文」（保守方向，不会漏扫，但会把英文轨里的中文注释一起扫到）。
- **样式名不可信时，先跑 `structure_check.py --ass <ass>`**，不要在可疑文件上直接裁决。

## 3. Git Bash 会把路径里的反斜杠吃掉

### 现象

```bash
python apply_fixes.py --file "C:\tmp\x\a.ass" --dry-run
# Python 收到的实际是 C:tmpxa.ass，报「文件不存在」
```

或者更难查的版本：在 `python -c "..."` 里传 `r"\N"`，shell 先吃一遍、Python 再解释一遍。

### 为什么

Git Bash（MSYS2）的路径转换会把`\`当转义符处理。双引号**挡不住**这一层——
它在 shell 层就已经处理完了，Python 拿到的字符串里反斜杠已经没了。

同一台机器上还有第二个坑：`/tmp` 在 Git Bash 里映射到
`C:\Users\<你>\AppData\Local\Temp`，而 Python 处理 `/tmp` 时按 `C:\tmp` 解释。
**同一个路径串，shell 和 Python 看到的是两个不同的目录。**

### 怎么绕

- **命令里一律用正斜杠**：`"C:/tmp/x/a.ass"`。Windows 的 Python 全盘接受正斜杠。
- 需要子目录就先 `mkdir -p` 建好，别指望自己会创建。
- 冒烟测试**用真实的 Windows 路径**，别用 `/tmp`——否则你以为在测 A，其实在测 B。
- 在 Python 里写含反斜杠的字面量，用 raw string（`r"{\i1}"`）或双反斜杠。
- **传给 shell 的是路径，不是正则**。要让 shell 别解释任何东西，用单引号包住整段，
  只把数据留在单引号里面。

## 4. 大文件喂 subagent 之前必须先分片

### 现象

把整份 ASS（1500+ 行）或整个 srt 贴进 subagent prompt：
subagent 的结论开始「跳着来」——中间的段落整段没提，编号对不上，
`total_hits` 报 0 但明明有问题。

### 为什么

- prompt 有长度上限。截断是**静默的**：它不会报错，只是后半段不在模型眼里。
- 即使没截断，长输入的注意力分布也是不均匀的——中段的召回显著低于首尾。
- 更隐蔽的：**编号锚点会漂**。审计员一边读一边在心里数行，读到第 700 行时
  前面数错过一次，后面全偏。M2 实测的 srt_id 越界 15 次主要是这个来源。

### 怎么绕

- **先把文件切成片，一片一个 subagent**。切片用 `extract_slice.py`，
  它按 srt_id 切、带重叠区，且会检查非空率。
- **切片必须带 `srt_id` 前缀**，不要用「第 N 行」这种相对编号：

  ```
  # 对
  [617] 0:12:34.56-0:12:36.78 | EN: ... | ZH: ...

  # 错（换个起始位置就全错）
  第 1 行 | 0:12:34.56-0:12:36.78 | EN: ... | ZH: ...
  ```

- **切片为空时立刻停下**。`extract_slice.py` 现在会在非空率 < 50% 时 abort。
  空切片会让整轮结论基于空气，而报告上完全看不出异常——R1 曾因此作废重跑 11 次。
- **让 subagent 报 `srt_id`，不要让它报行号**。行号是它自己数的，会错；
  `srt_id` 是切片里印着的，抄下来不会错。
- 裁决/核对位置用 `show_ids.py`，不要临时写脚本——临时脚本的口径每次都不同。

## 5. 结构检查必须跑在语义判断之前

### 现象

一轮审计跑完，报告第一条理由是「短句重写，语义偏离」，人拿着这条去核对，
发现真正的问题是**那条 `srt_id` 根本定位不到**（越界 / 轨是坏的 / 没配对上）。

### 为什么

语义护栏（`lib/guard.py`）判的是「改前改后的文本」，它的前提是
**两个文本确实是同一行**。前提不成立时，它给出的理由全是基于错位的比较，
看起来很有道理，但完全没法用。

结构问题（轨错位、`srt_id` 越界、起点重合、缺 `srt_path`）会让后面所有判断失效，
而且**不会自己冒出来**——它只会表现为「结论看着有点怪」。

### 怎么绕

- **开工前先跑 `structure_check.py`**。`round_orchestrator.init_run()` 已经把它
  接成前置门禁：ABORT（退出码 20）不建 run，SUSPECT（21）放行但打摘要。
- **`--skip-structure-check` 只用于确认误报**，用完之后把放行理由写进报告。
- **结构问题只在同轨内比**。中英两轨起点相同是正常的（同一句话的两个语种版本必然
  同步起止），把它们算成「起点重合」会把每一行都报成违规。
- **判语义之前先剥 ASS 标签**。`lib/guard.strip_ass_tags()` 就是干这个的：
  `{\be3}该死！啊！` 里的 `3` 会被当成数字、`{\an8}` 的 `8` 同理，
  于是「删去数字 3」这种理由会被算出来——而观众根本看不到这些字符。

## 6. 一页速查

| 坑 | 一句话 | 该用的工具 |
|---|---|---|
| 厘秒精度 | 改时间用毫秒整数，别用小数秒 | `lib/time_fmt.seconds_to_ass()` |
| `track` 中文串 | 判轨道走 `style_to_track()`；判干净用严格口径 | `structure_check.check_track_enum()` |
| bash 吃反斜杠 | 一律正斜杠；别用 `/tmp` 做冒烟 | — |
| 大文件喂 subagent | 先切片、带 `srt_id`、空片即停 | `extract_slice.py` / `show_ids.py` |
| 结构先于语义 | 轨坏了，后面所有理由都是假的 | `structure_check.py`（开工前） |
| ASS 标签 | 判语义前先剥掉，观众看不到它们 | `lib/guard.strip_ass_tags()` |

> 本页的每一条都来自实测，不是推测。改动其中任何一条之前，
> 先在对应的实测样本上复现一遍——这些「坑」很容易被当成过时的经验删掉，
> 而它们每一条都曾经静默地毁掉过一轮产出。
