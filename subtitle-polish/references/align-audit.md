# 对齐审计（时间轴）

本文件回答一个问题：**字幕文本改对了，但它出现在对的时间吗？**

结案时若只看 `verify_fixes` + `cross_check`，答案是「不知道」——这两个脚本一个字都不读时间字段。实测一批 8 集双语成品全流程绿灯交付，压制方反馈「所有集都对不上轴，越往后偏得越多」，回头用音频测出 3 集各偏 2.4~2.9 秒。

---

## 1. 为什么必须对音频，不能对字幕

「字幕 vs 本片内嵌字幕流」是最容易想到的基准，也是**最危险的**：它默认了「内嵌流与音频同步」，而这个前提常常不成立。

实测同一套 WEB-DL（8 集），内嵌流与音频的关系：

| 集 | 对音频的累积漂移 | 判定 |
|---|---|---|
| E02–E06 | ≤ 0.41 s | 内嵌流可信 |
| E01 | **+2.44 s**（4 处 +0.48 s 阶跃） | 内嵌流本身错轴 |
| E07 | **+2.79 s** | 内嵌流本身错轴 |
| E08 | **+2.91 s** | 两条内嵌流都错轴 |

根因：**音频是英国版剪辑，字幕却取自国际版（US）**。两版在剪辑点相差 0.48 s 的整数倍，逐段累积成「越往后越偏」。

E01 三轴对照（同一段音频，分别比对各候选基准）：

| 比对对象 | 中位 | MAD | 斜率 | 全长漂移 |
|---|---|---|---|---|
| ASS 终稿（修前） | +0.76 | 0.64 | +0.000932 | **+2.44 s** |
| MKV idx3（US / 无标题流） | +0.76 | 0.64 | +0.000932 | **+2.44 s** |
| MKV idx2（UK 流） | −0.06 | **0.24** | +0.000158 | +0.41 s |

ASS 与 US 流数字逐位重合 → ASS 就是扒的 US 轴。**拿它当基准，校验再严也只是自证。**

> 结论：对齐审计的唯一可信基准是**音频本身**。字幕流最多用来做「轴归属判定」的候选。

## 2. delta 与判据

```
delta = 语音发声时刻 − 字幕显示时刻
```

正常应 **+0.10 ~ +0.20 s**（字幕略早于发声，观众才读得完）。

**判据不是「delta 是否为 0」，而是「分时段 delta 中位数是否平坦」。**

原因：delta 的绝对值里混着三层东西——字幕提前量（设计使然，+0.1~0.2）、引擎系统偏置（±0.3，见 §4）、真实漂移。只有**窗间中位数的极差**（跨时段是否越走越偏）才是纯的漂移信号。

`align_audit.py` 输出的四个数，各管一件事：

| 指标 | 含义 | 怎么用 |
|---|---|---|
| delta 中位 | 整集系统性提前/滞后 | 参考，**不作判据**（含引擎偏置） |
| MAD | 单条 delta 的离散度 | 衡量「文本与音频一致度 + 引擎精度」，>0.5 说明对齐质量差 |
| 斜率 × 时长 | 线性累积漂移 | 判断能否用线性补偿一次性解决 |
| **分时段中位极差** | **最大系统性残差** | **主判据** |

阈值按引擎取（`--tol` 可覆盖）：

| 引擎 | 默认阈值 | 依据 |
|---|---|---|
| `whisper` | 0.50 s | 实测从未改动过的集也有 0.30 s 极差 |
| `qwen` | 0.30 s | 实测干净集 0.08~0.18 s |

## 3. 引擎选择：粗筛与精测

两个引擎归一到同一种词级时间戳，统计口径完全一致，差别在精度。

| 集 | whisper MAD | qwen MAD | whisper 极差 | qwen 极差 |
|---|---|---|---|---|
| E01 | 0.200 | 0.150 | 0.280 | 0.360 |
| E02 | 0.170 | **0.100** | 0.300 | 0.180 |
| E03 | 0.200 | **0.100** | 0.440 | 0.195 |
| E04 | 0.180 | **0.075** | 0.260 | **0.065** |
| E05 | 0.180 | 0.120 | 0.410 | 0.440 |
| E06 | 0.230 | **0.140** | 0.380 | 0.180 |
| E07 | 0.210 | **0.140** | 0.350 | 0.285 |
| E08 | 0.240 | 0.160 | **0.560** | **0.560** |

qwen 的数字全部取自 **120 s 分块**（下面「分块长度」一节解释为什么必须是这个量级）。

**用法：**

- **whisper 是粗筛**。MAD 0.17~0.24，能稳定抓 >0.5 s 的错轴（E01/E07/E08 的 2.4~2.9 s 一眼可见），但 0.2 s 级残差分不清。
- **qwen 是精测**。MAD 0.075~0.16，能分辨 0.2 s 级残差——E04 的 +0.21 s 线性漂移就是它抓到的，whisper 当时报 −0.05 s。
- **两者一致时最可信**。E08 两个引擎各自独立测出 **0.560，一位不差**——这是这套方法里唯一一次跨引擎逐位吻合，也是「E08 真有问题」最硬的证据。

**两条禁令：**

1. **不要用 whisper 的斜率/中位当补偿量。** 实测 E08：whisper 中位 −0.40 s，qwen 中位 −0.10 s，差 0.30 s——这是引擎系统偏置，不是字幕偏。按 whisper 补会凭空造出 0.3 s 误差。
2. **whisper 判 FAIL 不等于要改轴。** 极差落在 0.3~0.5 s 区间几乎全是噪声，先换 qwen 复核再动手。反之 whisper 判 PASS 只说明没有粗错，不代表亚 0.3 s 级也对。

> 为什么不用 whisperX 的 `align()`：它按 segment 的 `start`/`end` **切音频**（`audio[:, f1:f2]`）再跑 wav2vec2。输入时间戳偏 2 s，切出来的窗口就是错的，结果跟着错——它对「轴已经错了」的字幕无能为力。Qwen3-ForcedAligner 的 `align(audio, text)` **不接收时间窗**，是「整段音频 + 整段文本」的全局对齐，原轴偏 3 s 也照样还原真实发声时刻。

### 分块长度：显存与精度的同一个旋钮

`tokens_qwen` 按块做全局对齐。**块长同时决定显存、耗时和结果的稳定性**，
所以在 8GB 卡上它不是可以随手写的常数。

实测（RTX 4060 Laptop 8G / bf16 / 基线 ~1040 MiB / 整集 2648 s）：

| 分块 | 峰值显存 | 单块耗时 | 8 集平均 | E08 极差 |
|---|---|---|---|---|
| 30 s | 3240 | 0.9 s | — | — |
| 60 s | 3500 | 1.1 s | — | 0.520 |
| 90 s | 4362 | 0.8 s | — | 0.560 |
| 120 s | 5938 | 1.3 s | **~60 s** | 0.560 |
| 150 s | 7872 | 2.9 s | — | — |
| 180 s | 7885 | **41.0 s** | — | 0.560 |
| 240 s | 7898 | **91.7 s** | ~550 s | **0.300** ← 错值 |

两件事：

1. **150 s 起顶到 WDDM 预算，静默溢出到系统内存。** 判据不是 `nvidia-smi`
   的绝对值，而是它与 torch 自报的差额：从 150 s 起 `nvidia-smi` 钉在 7898
   不动，`torch.cuda.max_memory_allocated` 却从 3756 涨到 6162——差额就是被
   驱动搬走的部分。它不报错，只变慢（1.3 s → 41 s）。
2. **240 s 不只是慢，结果是错的。** 同一集、同一字幕、同一模型，240 s 给
   0.300（PASS），60/90/120/180 给 0.520/0.560/0.560/0.560。**90 s 及以上
   逐时段数字收敛到厘秒**，说明 ≥90 s 是稳定区间，240 s 是溢出后的坏值。
   这个坏值曾让 E08 看起来是「whisper FAIL / qwen PASS 的双引擎分歧」，
   实际两边都是 0.560。

所以：`--chunk` 默认由 `plan_chunk()` 按空闲显存选（120 → 90 → 60 → 30），
余量常量 `QWEN_VRAM_HEADROOM_MIB = 600` 与 whisperX 项目
`core/qwen_pipeline/transcribe.py` 同值；探针 `free_vram_mib()` 与那边的
`free_vram_mib()` / `models_manager.get_free_vram_gb()` 是同一个
`torch.cuda.mem_get_info()` 调用，数字可直接对照。

**为什么调分块而不是调精度：** bf16 常驻 1849 MiB、fp32 3506 MiB，往低走
没有更省的形式（fp16 与 bf16 同宽），而 120 s → 240 s 多花 2.4 GB。
能退的是分段长度，不是精度。

## 4. 轴归属判定

多版本剪辑的项目，先判「哪条内嵌流跟音频是一伙的」，再决定能不能拿它当参考流。

```bash
python scripts/align_audit.py --sub 终稿.ass --asr-words asr_words.json \
    --compare uk.ass --compare us.ass
```

同一段音频分别与每个候选比对。判定分四态，**不是「挑 MAD 最小的那个」**：

| 结论 | 条件 | 退出码 | 该怎么办 |
|---|---|---|---|
| `RESOLVED` | 赢家自己过绝对门，且领先次优的裕度够 | 0 | 用 `chosen` |
| `AMBIGUOUS` | 有候选过绝对门，但差距在噪声带内 | 4 | 不猜；换 qwen 复测或人工确认 |
| `NO_CANDIDATE` | 没有一条过绝对门 | 2 | 片源可能不是这批字幕的版本 |
| `SINGLE_PASS` | 只有一条候选且它过 | 0 | 可用，但记 `cross_checked=false` |

两道门：

- **绝对门**：候选自己的分时段极差 ≤ 阈值（whisper 0.5 / qwen 0.3）
- **裕度门**：`次优 MAD − 赢家 MAD ≥ max(0.10, 赢家 × 0.4)`

E01 实测 0.22 vs 0.62 → 裕度 0.40，RESOLVED。0.22 vs 0.24 → 裕度 0.02，判 AMBIGUOUS——whisper 的 MAD 噪声带就是 0.15~0.25，这个差距说明不了任何事。

**为什么必须留 AMBIGUOUS 这个出口**：`min()` 永远有返回值，四条流全是 0.62 时它照样宣布一个赢家。拿错轴的后果不是「没修好」，是**把对的改坏**。

**同族合并**：MAD 差 < 0.02 且锚点数相同的候选是同一条轴的两个变体（SDH / 非 SDH），报告里合成一族，不再像「四选一」：

```
轴族 2 个：
  S06E01.s0.uk.srt  S06E01.s2.uk.sdh.srt
  S06E01.s1.us.srt  S06E01.s3.us.sdh.srt
判定 RESOLVED —— S06E01.s0.uk.srt（MAD 0.220）领先次优 0.400 ≥ 0.100
```

抽完流直接判轴（一次 ASR 比对全部候选，`--credential-target chosen` 把凭据写在胜者旁边）：

```bash
python scripts/extract_subs.py --media S06E01.mkv --out streams --axis
```

也可以反过来验：拿 `align_patch.py --ref <候选流>` 干跑，若偏移是**平滑的单一值**或 0，说明这条流和当前字幕同轴；若打出**整数处阶跃**，说明它是另一版剪辑。

也可以反过来验：拿 `align_patch.py --ref <候选流>` 干跑，若偏移是**平滑的单一值**或 0，说明这条流和当前字幕同轴；若打出**整数处阶跃**，说明它是另一版剪辑。

## 5. 三种修复手段

| 现象 | 手段 | 命令 |
|---|---|---|
| 线性漂移，无阶跃 | 线性补偿 `off(t)=k(t−t0)` | `--slope K` |
| 剪辑点阶跃 + 有可信参考流 | 逐条重定时 | `--ref ref.ass` |
| 剪辑点阶跃 + 无参考流 | 分段常数曲线 | `--spec audit.json` |

**线性补偿**：`--origin` 默认取首条字幕起点，保证开头不动、只补末端。实测 E01 +0.000096（末端 +0.25 s）、E04 +0.000081（+0.21 s）、E07 −0.000087（−0.23 s）。

**逐条重定时**：用英文文本 LCS 建映射，未匹配条按前后锚点的偏移插值（不是按索引平均，避免阶跃处跳空）。E01 实测 728/728 全匹配，打出 4 处 +0.48 s 阶跃，与手工排查结果一致。

**分段曲线**：`align_audit --json` 里带 `curve` 字段（局部中位滤波 + BIC 选段数 + 最小段长 + **方向感知单调** + **首段归零**）。这些约束都不能省：

- **局部中位滤波**：全局 MAD 剔除在这里不够用——阶梯型偏移会让中位数落在两级之间、MAD 被撑大，阈值放宽到 ±3.5 s，尖峰全被放进来，接着把分段边界带偏。实测真值第 2 级在 1337.9 s，被拉到了 1102.7 s，中间 236 s 会多推 0.44 s。
- **最小段长**：点数不足的窄段常数不可信，且会制造假阶跃，必须并入邻居。
- **方向感知单调**：偏移只会沿一个方向累加不会回退，但**方向本身可能是负的**（字幕被推晚 → delta 递减）。早期版本写死 `run = max(run, c)`，遇到递减样本会把整条曲线夹平、末尾一个离群段反转成正向——照它施加会把字幕推得更偏，是这次注入测试抓出来的。
- **首段归零**：对齐器与字幕起点存在系统性偏置（实测 base −0.279 s），不减去就会把整集平推一段，反而制造新偏移。

> 判 PASS 的集不输出 curve。残余多是噪声，拟合出的曲线没有物理意义，误用会平白制造偏移。

**实测精度**：拿已知偏移做闭环注入测试（§10），曲线法能恢复 **85~90%** 的偏移量，残余 0.1~0.2 s。阶梯型（末级 88%）与线性型（86%）一致，说明是**随位移量成比例的少测**，不是某一种形态的特例。

机制尚未定位：可能是块内对齐把 token 拉进了给定音频段，也可能是首词锚点的系统偏置，两者都没有单独验证——别把它当已证结论用。

**二轮不值得做**。对已修过的 E03 再测一次，残余极差 0.230 s、斜率 −0.11 s，与一轮后复测逐位相同（中位 +0.020 / MAD 0.120）——说明聚合指标可复现到 0.01 s、残差是真的。但二轮拟合出的可修量只有 **0.10 s，且形态是一个孤立阶跃**：那是拟合噪声，不是残差，施加它只会平白引入一个假阶跃。

**0.1~0.2 s 就是这条链路的终点。** 想要更紧，得改输入（见 `build-timeline.md`：先判轴，多数片源本来就有同轴流），而不是在对齐算法上继续加轮次。

## 6. 为什么改时间要独立于改文本

`align_patch.py` 刻意**不依赖 srt_id 配对**：`off(t)` 是纯时间函数，对 ASS 英文轨、中文轨、配套 SRT 各自独立施加即可。

这避开了一个真实的坑：E04 的 SRT 有 750 块、英文轨 749 条，按条配对的脚本直接跳过 SRT（`[skip SRT] 750 vs 749`），结果 ASS 改了 SRT 没改，两套不同轴。用纯时间函数施加，条数不等完全不影响。

写盘也只替换 `Dialogue:` 行的 Start/End 两个字段，其余字节原样保留（实测 1732 行变动，去掉时间字段后 0 处差异）——不重排样式段、不丢注释、不动 `[Aegisub Project Garbage]`。

## 6b. 改完之后：记账、复测、可撤销

`align_patch --write` 之后会自动做三件事，缺一不可：

| 动作 | 为什么 |
|---|---|
| 写 `log.jsonl`（`action=retime_curve`） | 否则 `--rollback batch=` 回滚完文本、时间还错着，**回滚本身变成新的错误** |
| 让时间轴凭据失效（`patched_at > computed_at`） | 闸门立刻转 UNVERIFIED，逼你复测 |
| 记 `backups.jsonl` | `.bak` 不进 git，至少要能枚举、能对上是哪次操作 |

撤销一次曲线：

```bash
python scripts/align_patch.py --sub a.ass --revert
```

从记录的 `backup` 整文件还原（逐字节），并补记一条 `revert_curve`。**不要**用
`apply_fixes --rollback` 撤曲线——那是按行反向加回去，会累积浮点误差，也处理不了
当时被钳位到 0 的条目。

`verify_fixes` 会把 `retime_curve` 单列成「待复测」，既不算通过也不算失败：
它动的是时间不是文本，「0 失败」不能替它背书。

## 7. 三个必须处理的坑

**① 分块切在句中**。强制对齐按块喂文本，块边界切断了句子，该行就会锚到块首——实测 `ass 602.12 → align 600.00`，差 −2.12 s。`--chunk` 的边界必须在目标块长 ±45 s 内找**最大字幕间隙**，前后再留 2 s 余量。

**② 离群点污染回归**。ASR 听错、译文漏词、片头片尾噪声的 delta 与时间轴无关，留着会把斜率拉飞：E08 首跑得 `min −43.46 s`、斜率 +0.000660，真实值 −0.000080。必须按 `|delta − 中位| > max(1.5, 6×MAD)` 剔除（实测每集剔 34~59 条）。

**③ 把「内嵌流对齐」当验收**。见 §1。这条最贵：上一轮 handoff 就是这么得出「E02–E08 全部 0 偏差」的，错了整整一轮。

## 8. 命令清单

```bash
# ① 审计（视频直接给，自动抽 16k 单声道）
python scripts/align_audit.py --sub S06E01.eng.ass --media S06E01.mkv \
    --report .subtitle-polish/reports/align-E01.md --json .subtitle-polish/align/E01.json

# ② 粗筛过了、要精测 → 换引擎
python scripts/align_audit.py --sub S06E01.eng.ass --media S06E01.mkv \
    --engine qwen --model /path/to/qwen3-aligner-0.6b

# ③ 轴归属
python scripts/align_audit.py --sub 终稿.ass --asr-words w.json \
    --compare uk.ass --compare us.ass

# ④ 修复（默认 dry-run，加 --write 生效，自动 .bak）
python scripts/align_patch.py --sub a.ass --sub a.srt --slope 0.000096 --write
python scripts/align_patch.py --sub a.ass --ref uk.ass --write --emit-spec step.json
python scripts/align_patch.py --sub a.srt --spec step.json --write

# ⑤ 复测（同一份 asr-words 缓存，秒出）
python scripts/align_audit.py --sub a.ass --asr-words w.json

# ⑥ 写凭据 + 过闸门（阶段 0 与结案都要）
python scripts/align_audit.py --sub a.ass --media m.mkv --write-credential
python scripts/timeline_gate.py a.ass --media m.mkv
```

模型目录：whisper 用 `large-v3`（首次会自动下载或指定本地目录）；qwen 需本地 `Qwen3-ForcedAligner-0.6B`。

> **两件常把人挡在门外的环境问题**（实测踩过）：
>
> 1. **换个解释器**。`align_audit` 需要装 `faster-whisper` 的那个 python，不一定是 PATH 上的那个。
>    先用目标解释器 `python -c "import faster_whisper, torch; print(torch.cuda.is_available())"` 确认，
>    再把它套在脚本前。系统 python 缺包时不要立刻下「这台机器跑不了 ASR」的结论——先找有没有现成的嵌入环境。
> 2. **`--model` 传绝对目录**。给名字 `large-v3` 会走 HuggingFace 下载，离线或网络受限环境直接失败；
>    有本地模型时传目录。同理，模型已在本地却仍去连网，会卡在超时上，看起来像「跑得慢」。
>
> 速度参考（RTX 4060 Laptop 8G，large-v3 float16，43 分钟音频）：约 5 分钟。
> 明显超过这个量级时先看是不是同机在跑别的重活——`beam_size=5` + `word_timestamps`
> 的瓶颈在 mel 提取，CPU 被抢就会掉到 1/8 速。GPU 功率掉到 20W 上下、pstate 停在 P4 就是这个信号。

> **HF 缓存目录陷阱**：`~/.cache/huggingface/hub/models--*/snapshots/*` 里全是符号链接，`transformers` 的 `cached_files` 会把路径当 repo_id 校验，报 `Repo id must use alphanumeric chars...`。把 snapshot 内容复制成实体目录再用（1.7 GB，`shutil.copyfile` 约 1.4 s）。

## 9. 结案口径

字幕交付前三条都要过，而且**每条只有三态**（PASS 0 / FAIL 2 / UNVERIFIED 3）：

```bash
python scripts/verify_fixes.py --batch-id <ts>    # 改的东西写进去了
python scripts/cross_check.py  --batch-id <ts>    # 写进去的是这句该有的译文
python scripts/align_audit.py  --sub <ass> --media <片源>   # 写进去的东西在对的时间
```

第三条**不能省**，也不能用「对过内嵌字幕流」代替。上一轮的教训是：前两条全绿、8 集全"通过"，实际 3 集偏 2.4~2.9 秒。

报告里必须写明「本次验证覆盖范围」——测了几集、用的哪个引擎、极差多少，别让「N 通过」被读成「全文正确」。

## 10. 闭环验证（注入真值）

链路本身也要验：拿两集已对齐的成品，用**独立注入器**（不 import 本 skill 任何模块）施加已知偏移，再走一遍 `检测 → 精测 → 修正 → 复测`。注入参数由测试方定、管线不知情。

| 集 | 注入 | 粗筛极差 | 精测极差 | 修正 | 复测极差 | 对真值（中位/P95/最大） |
|---|---|---|---|---|---|---|
| E03 | 3 处阶跃 +0.52/+0.44/+0.61，末端 +1.57 s | 1.470 | 1.560 | 曲线 | **0.230** | 0.09 / 0.20 / 0.41 s |
| E06 | 纯线性 `0.0007×t`，末端 +1.83 s | 1.610 | 1.590 | `--slope` | **0.170** | 0.14 / 0.25 / 0.27 s |

阶跃幅度刻意取不等值，避免拟合器「猜中」真实素材的 0.48 等距。E03 三个阶跃边界拟合到 613.6 / 1341.0 / 2073.8，真值 611.3 / 1337.9 / 2074.5，误差 ≤3.1 s。两集文本改动均为 0，ASS 双语轨与 SRT 保持同步。

**这次测试抓出的 bug**：曲线拟合早期写死 `run = max(run, c)`，假设偏移单向增大；遇到「字幕被推晚、delta 递减」的样本会把阶梯夹平，再由一个离群窄段反转成正向 +1.26——照它施加比不修更糟。同时窄段离群点会把阶跃边界带偏（真值 1337.9 s → 拟合 1102.7 s，中间 236 s 多推 0.44 s）。修法是方向感知单调 + 最小段长 + 局部中位滤波，见 §5。

**已知限制**：单轮恢复 85~90%，残余 0.1~0.2 s（随位移量成比例少测，机制见 §5）。二轮实测没有可修内容（可修量 0.10 s，形态为孤立阶跃＝噪声），**这条链路的终点就是 0.1~0.2 s**。要更紧只能改输入——先判轴，别对着本来就同轴的流做对齐。

## 12. L0 结构哨兵（秒级，不加载模型）

```
python scripts/precheck_timeline.py S06E01.ass --media S06E01.mkv --baseline 16.9
# PASS 0 / SUSPECT 2 / UNVERIFIED 3
```

四级检查，全部不需要 ASR：

| 项 | 判据 | 判定 |
|---|---|---|
| 包络 | 首条 ∈ [−0.5, 60] s；末条 ≤ 片长+2 s | 越界 SUSPECT |
| 尾部缺口 | 末条距片尾 > max(30 s, 3%)，**且那段还有对白** | SUSPECT |
| 空洞 | 中段无字幕 > 300 s | INFO（剧集常见） |
| 密度 | 条数/分钟 偏离同批基线 > 2× | SUSPECT |

### 一个被否掉的判据

最初想做「fps 指纹」：`末条/片长` 命中 0.9590（=23.976/25）就判帧率错配。**实测行不通。**

正常字幕的末条本来就落在片长的 0.90~0.99 之间（E01 实测 0.9688），比值同时受「片尾留白」和「帧率换算」两个未知量影响——**一个端点解不出两个未知数**。按 0.9688×1.0427 去修，整片会被推 110 秒。

改成「尾部缺口 + 该段有没有对白」：差多少秒是观测值，有没有声音是验证过的，两者都成立才算问题。真因可能是截断、帧率错配或基准错位，报告里列出来，但**不假装能分辨**。

### 拟合诊断：`spec_from_pairs` 现在会拒绝

`align_audit --json` 里的 `fit` 字段：

```json
{"verdict":"FIT_OK","p90":0.13,"r2":0.94,"segs":4,"direction":-1,
 "breaks":[],"hit_max_seg":false,"hit_min_pts":false}
```

- `direction` 由 **Theil-Sen 斜率**给出，不再比较首末两段——末段常是合并不全的窄段，
  用它决定方向，一翻向就会把整条曲线夹平、末尾反转（v1.4.0 那次的 +1.26s 就是这么来的）
- `p90 > 0.4` → `FIT_REJECTED`，`curve` 为 `null`，`align_patch` 拒绝施加。
  阈值来由：正常阶梯拟合残差 P90 实测 0.13s，方法地板 0.1~0.2s，0.4 是地板的 2 倍
- `breaks` 记录相邻段的反向冲突（> 0.15s）。**不夹平也不反转**——那两件事只有人能判，
  可能是真实重剪接
- `hit_max_seg` / `hit_min_pts` 表示拟合顶到了参数上限，实际形态可能更复杂

被拒时改用 `--slope` 做线性补偿，或分区段手工处理。**不要**把 `FIT_REJECTED` 当成
「拟合失败重试一下」——它说的是「这批数据不是分段常数形态」，重试没用。

### 边界（必须写在帮助里）

> **L0 PASS ≠ 轴对。** 结构性正常但整体平移 0.3 s，它看不出来。L0 只负责排除明显错，把十分钟的 ASR 留给「值得跑」的样本。
