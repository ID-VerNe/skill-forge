# 判断归 LLM，脚本只做定位

本文件规定 **谁来做判断**。它参与决定 8 类里每一类的产出质量，所以放在顶层而不是某一类的附录里。

## 一条结论

> **能用上下文判断的，就交给 LLM；脚本只负责让它少读点无关材料。**

这条适用于**全部 8 类**，不只是第 8 类。

## 为什么

脚本判据是「字符串是否满足某个条件」。LLM 判据是「这句话在这个位置、这个语境下是否成立」。

两者的能力差在三个地方：

| 差距 | 脚本 | LLM |
|---|---|---|
| **召回** | 上限就是规则本身。词表没列的写法 = 不存在 | 读得懂同义改写、反讽、隐喻、上下文呼应 |
| **精度** | 只能判「像不像」，判不出「是不是」 | 能判说话人是谁、在骂人还是在复述 |
| **代价分布** | 漏报无感（报告照样说「完成」） | 漏报会有感觉（它知道自己没细看那几句） |

具体到字幕上，这三条差距都是实打实的：

- 第 3 类语义反转：「`as hard as it's gonna get` 译成『会变难』」——任何正则都写不出这条规则。
  跟前一句「今天就是最难的一天」的呼应才是判据，而那在上一行里。
- 第 4 类语境错译：「`Get in!` 译成『进去』」——`Get in` 译「进去」本身没错，
  错在这是催人上车。要判它，得知道前一秒画面在车边。
- 第 5 类专名：`Hennessy` 是不是打错，取决于指白兰地还是改装厂（Hennessey）。**拼写本身两边都对。**
- 第 7 类翻译腔：`So` 译「所以」算不算翻译腔，取决于这句是不是承接上文。上一轮实测过：
  规则判 11 处，人工确认只有 4 处真有病。
- 第 8 类：`mainland` / `Virgin Islands` / `mother hen` —— 见 `inclusive-language.md` 开头的例子表。

而脚本擅长的事恰好都很窄：**找位置、去重、配对、比对字节**。所以分工就该这么切。

## 分工表

| 环节 | 谁做 | 产出 |
|---|---|---|
| 切片、配对、异常标记 | 脚本 | `slices/*.txt`，一 block 一行 |
| 时间轴体检、标点预检、台账比对 | 脚本 | 确定性报告（不涉及语义） |
| **出线索**（锚点位置 + 上下文段） | 脚本 | `seed-*.json`，**只有位置，没有结论** |
| **读全文下判断** | LLM subagent（并行） | 问题清单：类别 / 严重度 / 原文 / 现译 / 问题 / 建议 |
| **反驳误报** | LLM subagent（adversarial） | 确认 / 驳回 / 存疑 |
| 合并去重、白名单核对、交人裁 | 主 agent | `audit-report.md` → `fixes.json` |
| 执行改动、核验落盘、回滚 | 脚本 | `log.jsonl` / `.bak` / 快照 |

**注意表的第二列不是「脚本 vs LLM」二选一**：脚本在流程里出现三次（切片、出线索、执行），
LLM 在流程里出现两次（审计、验证）。**没有一次是脚本在做判断。**

## 并行 subagent 怎么切

### 切分单位：切片文件，不是类别

**按切片切，不按类别切。** 一个 subagent 负责 `_p1.txt` 里的 `[start, end]` 块，
在这一次读里把本轮范围内的**所有类别**都过一遍。

为什么不是「每个类别一个 agent」：

1. **上下文只有一份。** 判第 3 类要读前一句，判第 4 类要读整个场景，判第 8 类要看说话人是谁。
   按类别切开，每个 agent 都得重读同一片，token 反而更多，而且读到的上下文更窄。
2. **类别之间有交叉。** 「译得对但会挨骂」和「译得不顺」的区别，只有同时看到两类才能守住
   （`category-taxonomy.md` §8 与第 7 类的边界）。分给两个人判，边界就没了。
3. **切片已经切好了。** 1–7 类和第 8 类共用同一批切片文件，这是 `rounds-spec.md` §2 的既定约束。

### 片数：`max(1, round(块数 / 700))`，小文件短路

| 单文件块数 | 怎么办 |
|---|---|
| ≤ 200 | 主 agent 直接审，不另起 agent（省一轮往返，判断质量不降） |
| > 200 | 每片一个 subagent，并行跑 |

700 块是经验值：再大，一个 agent 读到尾部时对开头的记忆已经淡了，跨段呼应会漏；
再小，上下文被切碎，第 1 类的配对错位判不出来（错位往往跨 20 块以上）。

**这条阈值不许因「我已经读完整切片了」自行放宽**——那是模型给自己找的省事理由。

### 并行不等于可以省检查

多个 subagent 并行跑时，主 agent 在等返回的期间**做什么**决定了这一轮的质量：

- **可以**：跑 `scan_seed.py` 出锚点（等 subagent 回来对照，看它漏了什么）、
  跑 `regression_check --ledger` 备下一轮的台账、跑 `precheck_punct`。
- **不可以**：自己也去读切片做判断然后塞给 subagent。那是重复劳动 + 污染独立性
  （`prompt-injection.md` 规则 2）。

**subagent 返回后，主 agent 必须做的三件事**：

1. **对照锚点找漏**：某段有锚点、subagent 一条没报 → 回问它「这一段的 X 你怎么判的」，
   而不是直接算它干净。这是脚本在这一环唯一的用处——**当漏检探测器**，不当判据。
2. **去重**：相邻切片有 100 块 overlap，同一条问题会报两遍。按 `(file, srt_id, category)` 去重。
3. **白名单核对**（仅第 8 类）：subagent 给了替换词、而该词在白名单里的，退回 L3 只标注。

### 每个 subagent 的 prompt 必须包含

| 段 | 内容 | 缺了会怎样 |
|---|---|---|
| 切片路径 + `[start_block, end_block]` | 它负责哪一段 | 报出来的 id 归属不明，合并时对不上 |
| 项目背景 | 中性领域事实（节目类型、机械型号） | 专名判断失准 |
| `round_scope` | 本轮只审哪几类 | 会审 8 类，把第 7 类的润色意见混进主修 |
| `seeds`（第 8 类） | 锚点 + 上下文段 | 要么从头读（浪费），要么只读锚点（召回退化成词表） |
| `inclusive_list`（第 8 类） | 白名单 | 会把 `母头` 报成敏感词 |
| `ledger` | 历史改动（**不含 reason**） | 会把上一轮的改动当新发现重报，或顺着上轮理由连错三轮 |

**不许包含**：主 agent 预扫结论、上一轮的判断理由、任何「这条应该译成什么」的答案。
理由见 `prompt-injection.md`。

## 什么时候脚本可以当判据

只有一种情形：**判据本身是确定性的，且不涉及语义**。

| 判据 | 为什么脚本可以判 |
|---|---|
| 盘面 == log 里的 new_text | 字节比对，无歧义 |
| 中英是否配对、srt_id 是否连续 | 结构关系，与意思无关 |
| 时间轴分时段中位极差 | 数值比较 |
| 同一行是否被连续 N 轮改动 | 台账查询 |
| 标点是否规范（`……`→`…`） | 字符类，规则闭合 |

反过来，只要判据里出现「意思」「语境」「合适不合适」「该不该」，就**必须**交给 LLM。
第 8 类的词表命中看起来像前者，实际是后者（同一个词两种语境两种结论），所以它也只是线索。

## 这套分工的失效模式

写在这里，是为了下一轮改动时不至于把它改回去：

| 症状 | 真正的病因 | 别这么治 |
|---|---|---|
| 报告「无候选」，但人肉一看有 | 锚点被当成判据，subagent 只读锚点 | 加更多关键词（只会把上限又抬高一点） |
| 同一条被反复报、改来改去 | 台账带了 reason（顺着上轮逻辑推） | 提高阈值（掩盖症状） |
| subagent 报了 50 条，人裁掉 40 条 | `round_scope` 没填或填成「全部 8 类」 | 让它「谨慎点」（它会改成漏报） |
| 第 7 类的润色混进主修 | 类别切给不同 agent，边界判据丢了 | 把第 7 类也交给同一个 agent（正是应该做的） |
| 并行 6 个 agent，结果互相矛盾 | 没给 `[start_block, end_block]`，两个 agent 都以为自己负责全片 | 加 agent 数量（矛盾来自范围不明） |
