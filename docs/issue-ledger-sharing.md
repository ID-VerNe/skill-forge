# 8 集批量：台账该共享还是各自独立？

> 状态：**讨论，不做决策**。本 issue 只摆证据和权衡，不给结论。
> 前置：v1.14（#24）的 A/B 批次改完再议——那两批会动 `--work-dir`、`--adopt`、log 回写，
> 先改再谈，否则讨论的是会变的代码。

---

## 一、要讨论的是什么

现在一个 `.subtitle-polish/` 对应一集：

```
S06E01/.subtitle-polish/log.jsonl    131 条
S06E02/.subtitle-polish/log.jsonl    ...
S06E08/.subtitle-polish/log.jsonl    ...
```

问题：**8 集连着做时，台账要不合成一本？**

| 方案 | 形态 |
|---|---|
| **A 各自独立**（现状） | 每集一个 work-dir、一本 log、一套 runs |
| **B 全共享** | 一个 work-dir，8 集的改动进同一本 `log.jsonl`，靠 `file` 字段区分 |
| **C 混合** | 台账独立，但**跨集可见**：术语表、白名单、`false_positive`、待定项共享 |

方案 C 是这次真正想讨论的东西——A 和 B 都太极端。

---

## 二、为什么这件事值得单开一个 issue

因为它**不是"文件放哪儿"这种整洁问题**，而是悄悄决定了四件互不相干的事：

### 2.1 它决定「第 1 集的裁决」能不能约束第 3 集

字幕组做整季，最难的不是单集内一致，是**跨集一致**：

- `the Smallest Cog` 在第 1 集译开「小齿轮」、第 5 集译成「最小的齿轮」——这不是错译，是不统一
- 主角的口头禅、修车行的车间术语、车型代号（`MGB GT` / `Escort RS2000`）必须跨集同译
- 同一个梗在第 2 集已经判过「不改，保留原文味道」，第 7 集不该被另一个 subagent 判成「要改」

现状：**每一集从零开始**。8 集跑完，跨集不一致没有任何人负责。这不是台账共享能解决的（那需要术语表），但台账共享是前提——**不共享就永远不知道第 5 集和第 1 集译得不一样**。

### 2.2 它决定回滚的粒度

- 方案 A：回滚第 5 集，不会碰到第 1–4 集。**安全**。
- 方案 B：8 集共一本账，`--rollback batch=<id>` 只动该批次的条目，理论安全；但 `--rollback-to rNN` 是**整本还原**（见 #24 的 B4），会把另外 7 集的记录一起打回去。

也就是说：**B 方案下 `--rollback-to` 必须重写或禁用**，否则任一集的回滚都会波及整季。

### 2.3 它决定 subagent 能不能跨集学

`false_positive` 现在的用途是"让清单只增不减"。它天然是跨集的：第 1 集判「`mother hen` 在夸人，不是问题」，第 3 集遇到同一句式时，让 subagent 读到这条记录，能省一次重复判断、也能防两次判断不一致。

但这件事**只在共享时成立**。独立台账下，`false_positive` 是一集一丢的。

### 2.4 它决定 `--work-dir` 的默认值能不能定死

#24 的 A4 要把 `--work-dir` 收敛成唯一默认值。如果将来要共享，默认值就得支持"向上找共同父目录"这类逻辑——**两类需求打架**。所以 #24 先按单集定死，本 issue 单独谈共享。

## 三、已知的约束（这些不是可选项）

| 约束 | 来源 | 对方案的影响 |
|---|---|---|
| `--work-dir` 传 `.` 必须报错 | #24 A4 / S06E01 H4（孤儿 log） | B 方案下"8 集共用一个 work-dir"会让每条命令都要绝对路径，误操作面变大 |
| `--rollback-to rNN` 是整本还原 | `round_orchestrator._restore` | B 方案必须改这里，否则跨集污染 |
| log 条目已有 `file` 字段（绝对路径） | `lib/log.py` schema | B 方案技术上可行，`file` 够用来区分 |
| `--auto` 隔离 log 需回写主台账 | #24 B1 / H3（74 条掉到 2 条） | 共享后回写逻辑要从"一本"变成"按 file 分流"，风险上升 |
| 快照 `rNN.ass` 是**整文件**副本 | `_record` | **B 方案下 8 集的 `r00..r11` 快照 = 8×12×150KB ≈ 15MB**，可接受；但如果 8 集共 work-dir，`rNN.ass` 该存哪一集？这是 B 的硬伤 |

## 四、方案对照

| 维度 | A 独立（现状） | B 全共享 | C 混合 |
|---|---|---|---|
| 跨集术语一致 | ❌ 无解 | ⚠️ 只能事后 grep 发现 | ✅ 术语表可显式维护 |
| `false_positive` 复用 | ❌ 一集一丢 | ✅ | ✅ |
| 回滚安全 | ✅ 天然隔离 | ❌ 需重写 `--rollback-to` | ✅ 同 A |
| 快照存放 | ✅ 清晰 | ❌ 无自然归属 | ✅ 同 A |
| 单条改动定位 | ✅ | ⚠️ 必须带 file | ✅ |
| 8 集跑完出总账 | ❌ 要手工拼 | ✅ 天然 | ⚠️ 要写合并脚本 |
| 改造成本 | 0 | 高 | 中 |

**初步倾向（未决）**：C。台账各自独立（保住回滚安全和快照归属），另加一层**跨集共享的只读知识**：

```
season-知识库（新建，不叫 log）
├── glossary.jsonl        术语表：英文 → 统一译法，8 集共用
├── false-positive.jsonl  判过"不是问题"的句式及其理由
├── pending.jsonl         跨集待定项（这一集没法定、要等后面剧情）
└── （只读输入，不是台账；不改它也能跑，改它只影响后续集）
```

理由：**共享的是"知识"，不是"账"**。账必须一集一本，因为回滚、快照、verify 都建立在"这一集的完整历史"上；知识天然跨集，且它是 append-only、不参与回滚。

## 五、需要回答的问题

1. **跨集术语表由谁维护？** 第 1 集跑完自动抽取专名进 `glossary.jsonl`，还是要人确认？误抽的代价是后面 7 集全错。
2. **术语表冲突怎么办？** 第 3 集剧情揭示 `the Cog` 其实是人名不指修车行，第 1 集的译法就得改——这个回填谁做？
3. **`pending.jsonl` 的语义**：第 1 集留下的待定项，第 5 集没解决，第 8 集结束还在——交给谁？
4. **单集要不要能独立交付？** 如果客户只要第 5 集，知识库缺失时能否降级跑通？（我倾向：必须能，知识库是加速器不是依赖）
5. **8 集是否并行跑？** 并行时知识库有写冲突，只能先读后写或加锁。串行跑最省事，但慢 8 倍。
