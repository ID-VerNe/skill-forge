## A 组：A1 三形态标签（本轮主要改动）

数据来自切片文件头注与 `extract_slice` 的 stdout。

| # | 检查点 | 期望 | 怎么取证 |
|---|---|---|---|
| **A-1** | 头注里是否**还有** `SRT_HAS_ASS_NONE` | **必须 0 次**。若有，说明跑的是旧代码 | `grep -c SRT_HAS_ASS_NONE slices/*.txt` |
| **A-2** | `PAIRING_OUT_OF_TOLERANCE(off=±N.NNs)` 是否出现并**带具体数值** | 有则每条都该带 `off=`，不允许出现光秃秃的 `PAIRING_OUT_OF_TOLERANCE` 无括号 | 贴出前 10 条原文 |
| **A-3** | `PAIRING_FAILED(srt_id=N)` 是否出现 | 允许出现，但**每条都要能指认「ASS 里真的没有这句」** | 若有，逐条给出 srt_id + 该块的 start/end + 你在 ASS 里查证的结果 |
| **A-4** | 「未配上」总数构成 | 报三条数：正常配上 / 超容差 / 无对应行，各占多少（分母是总块数） | `extract_slice` stdout 的 `pairing_failed: N/M (x%)` 那一行 |
| **A-5 ⭐** | **审计报告里是否还出现「漏译 / 译文缺失」类结论** | 这是本轮最关键的验收点。若出现，必须逐条标注它对应的是哪个标签 | 贴报告原文 + 对应头注 |

> **A-5 为什么是重点**：上一轮 R5 p1 报了 38 条假漏译，根因是「配对没成」被读成「漏译」。本轮改标签的全部意义就是消掉这个。如果报告里仍出现漏译结论，且它对应的块带的是 `PAIRING_OUT_OF_TOLERANCE`，说明**标签改了但 prompt 没拦住**——那是比原来更糟的情况，因为标签已经明说「不是漏译」了。

## 交付格式

1. **先给判定表**：上表每一条填「过 / 不过 / 无法判定 + 一句话依据」。无法判定的写清「缺什么数据」。
2. **再给问题报告**：遇到的所有问题，每条写
   - 现象（贴原始输出，不要转述）
   - 复现路径（命令 / 文件 / 行号）
   - 你判断的归属：**skill 缺陷** / **本次素材问题** / **agent 操作问题** / **不确定**
   - 若判为 skill 缺陷，指出**代码或文档的具体位置**
3. **最后单列「预期外」一节**：清单里没提但你观察到的任何异常。

> 三条硬要求：
> - **不要为了让我高兴而把「不过」写成「过」。** 本轮的目的就是找出还有哪些没修好。
> - **不要顺手改 skill 代码。** 只记录，方案我来定。
> - **贴原始输出，不要总结成「正常」「没问题」。** 「正常」两个字我无法核对。
